# Neura Runtime / Bridge HTTP API (V1 Draft)
Status: Draft v0.1 (V1 target)  
Applies to:
- **`neura_runtime`** (managed mode for `.py`)
- **`neura_bridge`** (attach mode inside a local `.ipynb` kernel)

Both backends MUST implement the same HTTP surface so the VS Code extension and agent layer can treat them interchangeably.

---

## 1) Goals
- Provide a **small, stable, localhost-only** API for:
  - executing Python code in a persistent session
  - inspecting runtime state (variables)
  - inspecting/profiling pandas DataFrames
  - interrupting long-running execution
- Return **structured outputs** suitable for rendering in VS Code UI and for agent evaluation.
- Enforce **budgets** (timeouts, output truncation, payload limits).

## 2) Non-goals (V1)
- Remote execution / multi-user sessions
- Streaming tokens or streaming execution output (polling may be added later)
- Sandboxing untrusted code (code executes with user permissions)
- Full object graph introspection (V1 focuses on DataFrames + basic variable metadata)

---

## 3) Transport & Security

### 3.1 Bind address
- MUST bind to `127.0.0.1` only in V1.
- MUST NOT listen on external interfaces by default.

### 3.2 Authentication
All requests MUST include:

`Authorization: Bearer <token>`

- Token is generated by the VS Code extension.
- Requests without valid token return `401 Unauthorized`.

### 3.3 Content types
- Request: `Content-Type: application/json`
- Response: `application/json; charset=utf-8`

### 3.4 Versioning
- Responses include `version` in `/health`.
- API compatibility is maintained for V1 within a minor version.
- Breaking changes require bumping the API version and updating extension accordingly.

---

## 4) Concurrency & Execution Semantics

### 4.1 Single active execution
V1 backends are **single-threaded for execution**:
- Only one `/eval` may execute at a time.
- If an `/eval` arrives while busy:
  - backend SHOULD return `409 Conflict` with `{ "ok": false, "error": {...} }`
  - extension is expected to serialize calls.

### 4.2 Persistent state
- The backend maintains a persistent Python namespace.
- `/eval` runs in that namespace and may mutate it.

### 4.3 Working directory
- `/eval` can set a `cwd` (workspace root) for file-relative operations.
- Backend SHOULD `chdir` for the duration of execution and then restore (implementation choice).

### 4.4 Timeouts
- `/eval` accepts `timeout_s`.
- If timeout is exceeded:
  - backend SHOULD attempt to interrupt execution and return an error payload
  - exact behavior depends on runtime (best-effort in V1)

---

## 5) Common Response Envelope

Most responses use:
```json
{
  "ok": true,
  "version": "0.1.0"
}
```

`version` carries the API version (`0.1.0`). A successful call also carries its
payload (`execution`, `vars`, `inspect`, `profile`, `last_error`, …). Failures
add `error`:

```json
{
  "ok": false,
  "version": "0.1.0",
  "error": {
    "type": "ZeroDivisionError",
    "message": "division by zero",
    "traceback": "Traceback (most recent call last): …"
  }
}
```

### 5.1 Which failures are HTTP errors

- **HTTP 4xx/5xx** is reserved for transport and protocol problems: `401` for a
  missing/incorrect token, `409` (`BusyError`) when another execution holds the
  slot, `413` for an oversized body, `415` for a non-JSON POST, `422` for an
  invalid schema, `503` (`RuntimeStoppingError`) while shutting down.
- **Domain failures** — an unknown variable name, a name that is not a
  DataFrame — return **HTTP 200 with `ok: false`** and a structured `error`, so
  a caller can tell "the runtime could not answer" from "the runtime answered:
  no".

## 6) Endpoints

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/health` | Liveness plus `status`/`busy`. |
| `POST` | `/eval` | Run code in the persistent namespace. |
| `POST` | `/interrupt` | Best-effort interrupt of the active execution. |
| `GET` | `/vars` | Bounded summary of user variables. |
| `POST` | `/inspect` | Bounded preview of a DataFrame variable. |
| `POST` | `/profile` | Budgeted statistical profile of a DataFrame. |
| `GET` | `/last_error` | Most recent structured execution error, or `null`. |
| `POST` | `/stop` | Stop the backend (the bridge keeps its kernel alive). |

`/eval` accepts `{"code": "...", "timeout_s": 30, "cwd": null}` and returns
`execution`:

```json
{
  "stdout": "hello\n",
  "stderr": "",
  "stdout_truncated": false,
  "stderr_truncated": false,
  "result_repr": "42",
  "result_kind": "value",
  "result_repr_truncated": false,
  "state_changed": true,
  "rich_truncated": false,
  "duration_ms": 3,
  "outputs": []
}
```

`outputs` holds bounded rich items (`html`, `image_png`, `dataframe`, `text`);
see [the runtime guide](../runtime-development.md#rich-output-capture-outputs).
`/inspect` accepts `{"name": "df", "n": 5, "timeout_s": 10}` and `/profile`
accepts `{"name": "df", "config": {...}, "timeout_s": 10}`; both clamp their
budgets and return `ok: false` for domain failures.

Every method is serialized through the backend's single execution slot, so the
namespace is never read while user code mutates it. Concretely: `/eval`,
`/vars`, `/inspect` and `/profile` share one slot and return `409` while it is
held, while `/health`, `/interrupt`, `/last_error` and `/stop` stay serviceable.

## 7) Handshake

Both backends print one flushed JSON line on stdout when they are ready:

```json
{"neura_runtime": true, "port": 51243, "pid": 12345, "version": "0.1.0"}
```

```json
{"neura_bridge": true, "port": 51243, "pid": 12345, "version": "0.1.0",
 "kernel": "ZMQInteractiveShell", "kernel_name": "python3",
 "connection_file": "…/kernel-1234.json"}
```

The marker field (`neura_runtime` or `neura_bridge`) tells the client which
backend it attached to; everything after the handshake is identical. The token
never appears in the handshake or in logs.
